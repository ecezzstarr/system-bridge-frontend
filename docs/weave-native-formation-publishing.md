# WEAVE Native Formation Workshop — publishing without a new server build

## Purpose

**Still Water**: Hope supplies direction; Administrations provides the
durable structure through which people can continue working.

An approved Administration source operator can use
\`/admin/native-foundry\` to construct new company pages and bounded
features/systems as **validated, versioned data** inside Weave.
Publishing an approved module never runs Docker, shells, GitHub Actions or
Oracle host deployments. Once this engine itself has been released to the
host, subsequent native publications become available through the live
database. This is not automatic creation of arbitrary backend code.

## End-to-end company creation

1. **Choose department**: Hope (Bridger), Stability (Agent), Dream Lovely
   (Client) or Administrations (A Time).
2. **Choose type**: page; feature with an installed company route action;
   system with persisted per-user steps.
3. **Write in your own cadence**: title, explanatory body, section copy,
   glass cards and step instructions are editable without code.
4. **Choose quality and visual blocks**: Crystal, Premium or Plus-style
   render settings; installed WebGL glass kingdom, mechanized equipment,
   or Still Water scene. Reuses the File Folder city material atlas for
   real three-dimensional objects, together with physical glass shading
   and mobile-bounded rendering.
5. **Review the live preview** in the same workspace. Reorder, edit,
   add or remove supported blocks.
6. **Save draft version**. The server checks every element against a
   strict schema: number of blocks, length of writing, link destinations
   and step keys.
7. **Publish intentionally** by typing \`PUBLISH WEAVE MODULE\`.
   A PostgreSQL transaction locks the department/address slot,
   verifies the expected published ID, archives the previous live
   version and promotes the selected immutable draft, then logs
   the authorized operator.
8. **Operate** from
   \`/weave-modules/<department>/<slug>\`. Published modules are surfaced
   automatically in each department workplace, only to the matching role.
   For a system, a worker can mark their own permitted steps completed;
   progress is stored per authenticated user and release version.
9. **Restore or withdraw**. An archived version is copied into a new
   draft before explicit publication. Administrations can also
   type \`UNPUBLISH WEAVE MODULE\` to withdraw a live page without
   deleting its version or movement history.

### Live company work-intake capability

A feature or system may also contain one or more **intake** blocks with
validated short text, long text, optional questions and fixed choices.
An authorized department member can submit the finished intake from
the published page. WEAVE stores an immutable submission receipt and
timestamp; the appointed Administration operator may review the latest
80 records for that department module in the Native Formation Workshop.

Intake is a work-record mechanism, not a financial settlement, identity
verification, payroll instruction, AI-generated code, approval workflow
or secret collection service. Published field keys are validated at
write time. Each user has a 30-second per-form submission limit;
a concurrent release withdrawal cannot accept a stale new submission.

Forms are installed components that do not require Git commits or
Oracle rebuilds for their definitions. New form action types or
external connections require independently reviewed code.

Existing Client File Folder ownership, paid systems, financial approvals,
source code and department assignments are unchanged. The new Plus-style
visual option does not grant a Plus File Folder, equipment, employees or
any paid service. System step completion does not create a transaction,
verify a sale, approve an order or make an income guarantee.

## Two distinct release paths

### WEAVE native runtime publication

\`\`\`text
Authorized Administrations
  → purpose and department
  → installed visual/operational building blocks
  → live preview and validation
  → immutable DB draft
  → explicit publish or restoration
  → atomic active version
  → department runtime page
  → individual recorded work
\`\`\`

No GitHub access or Oracle rebuild is needed after this runtime engine
is installed. The source code is already running and interprets the new
versioned module data. A refresh retrieves the current published version.
No arbitrary code is evaluated from database content.

### New technical capability / engine upgrade

\`\`\`text
New or changed executable capability
  → Company Code Workshop controlled source branch
  → source diff review and tests
  → GitHub protected merge and Production Check
  → verified host release/rollback
  → installed component available to Native Formation Workshop
\`\`\`

This path remains necessary for changes to authorization, payments,
external API credentials, new arbitrary behavior, database mechanisms or
React/Three.js component implementations. The verified-continuity workflow is review-only while Oracle remains the
active company host. It can report a verified GitHub main SHA but cannot
dispatch a deployment. Administrations must use the original manual Release
Workshop for executable server updates. Future automatic owned-host updates
require a separately authorized host-specific worker.

## Permissions and safety

- Native publishing is restricted by \`requireWorkshopAuthorization\`,
  which checks a live Administration session and designated operator
  identities. Ordinary department accounts cannot publish.
- Runtime reading is checked by \`getAuthUser\` and a role-to-department
  map on each request. A Legion cannot reuse their suspended Agent/Bridger
  privileges. Administrations can inspect every department.
- The displayed content is inert React text, not HTML script execution.
  Links only accept bounded relative WEAVE routes. No JSX evaluator,
  shell, dynamic imports, browser-issued SQL, Docker socket, remote
  executable templates or arbitrary production file writes exist.
- Every module version is immutable. Concurrent changes to the same
  department/slug are serialized; stale publish/withdraw commands fail.
- Progress is for the authenticated person's current published system
  version only; the module cannot mint System Switch, send payments,
  approve people or alter other users' records.
- Withdrawn versions are not served by runtime endpoints. Future
  modules are discoverable through the role's department workspace only
  after publication.
- Native content uses the existing WEAVE database. It depends on
  database availability and backups; runtime publication cannot recover
  a failed host or missing database automatically.

## Quality verification

Before activating on production, verify the initial PR and deploy the
engine through the existing reviewed release pipeline. Check the physical
3D preview on mobile and desktop; view, publish, update, withdraw and
restore each department; confirm role restrictions and Legion exclusion;
test concurrent publish attempts, stale versions, system progress isolation
and persistence across browser restart. Take a database backup, ensure
the app role can create the required tables (or apply the equivalent
controlled schema migration), and review production query costs.

This first native workshop supports a finite safe library of functional
blocks. New forms, integrations, inventory actions, customer workflows,
procedural mesh libraries or richer visual materials must first be added
as audited, tested engine capabilities. Once installed, those can be
configured and reused without further server builds.
