# Client-owned worlds: identity, work and visible growth

## Ownership comes from the record, not from the picture
A verified and activated File Folder provisions one persistent `weave_open_world_domains` record linked to the Client and File Number. Reopening the world or rebuilding a scene must never create another entitlement or transfer that domain. Standard, Pro, Premium and Plus remain purchased/approved tiers with distinct exteriors.

The approved illustrated atlas is a map of landmarks, **not** a saleable fixed building with permanently assigned names. A real purchased Client domain belongs to an actual position in the live 3D land. Its owner sees their verified personal Client name on the map and their own castle; only that owner can enter the private File Folder.

An uncommissioned Client domain is visible to outsiders as a generic forming domain. Its actual Client name, File Number, private business plans, files and unfinished systems are not published. Once its Customer Door is commissioned for public sale, the real, published **business** name comes from `client_business_stores` to the public world feed. A Client's private personal name does not become public merely because a payment succeeded.

## Real movement instead of fake game progression
A File Folder is a persistent operating environment. It develops through authorized systems and recorded actions, not fantasy quests or invented income. The shared 3D exterior may visibly grow when `client_built_systems` become active; inactive, unpurchased and unpublished systems must not be shown as operating. The first capped geometry pass adds small wings according to the verified system count. It is not an accounting or earnings claim.

The Client's occupation is a basis for how actual capabilities are assembled, not a compulsory visual template. A photographer's potential business system involves:
- Public Customer Door for bookable shoots, event enquiries, package offers and documented orders.
- Scheduling and actual event assignments with a Client-approved employee/Legion where authorized.
- Private asset intake, editing and revision queue with storage rights, consent and usage controls.
- Customer review, delivery, print/licensing products, payment reconciliation and receipts.
- Repeatable marketing support through the Bridger/Hope studio and, where relevant, Agent/Stability distribution.

These are **future capabilities**, not features falsely claimed to be commissioned by this nameplate release. Each becomes live only when the corresponding authorized workflow, persistent database schema, transactions, permissions and tested endpoint exist. A completed commission is a recorded business action; an earnings display must always be based on settled receipts.

## Visual direction
Preserve approved image textures. The web overlay supplies the owner's dynamic name in the map without rewriting image pixels. Real Three.js castle meshes are the interactive source of truth. Future work should add realistic interiors, photoreal materials, an operating workshop camera, polished water and glass, and calibrated mobile detail levels. A castle should open the actual authorized workshop or Customer Door; decorative buttons must not imply non-existent tools.

## Release constraints
Owner identity is read from `/api/client/company-loop-connections` using existing Client authentication and private no-store cache. Public `/api/system-switch/open-world` must never serialize that private name until a separately commissioned business name is deliberately public. The existing purchase, privacy, relocation, tier and role rules remain authoritative.

This branch is source work; a successful deployed mobile inspection, actual Client purchase workflow, permission tests and performance check remain required before production.
